# Перенос на VPS и подключение оплаты

## Что подготовлено

Переносимый сервер Node.js в `server/` обслуживает именно текущий дизайн из `pages/`. Он не зависит от Cloudflare, ChatGPT-входа или старого React-приложения. GitHub Pages продолжает работать как демо.

В комплекте: PostgreSQL, миграция, серверная форма заявок, вход в `/admin`, поиск и пагинация, ручная смена статуса с комментарием и журналом, проверки полей и редакций документов, защита от повторных заявок при сетевых сбоях, ограничение попыток, HttpOnly-сессии, проверка Origin и CSRF, Docker Compose и Caddy для HTTPS.

Это основа для приёма заявок, **не готовая автоматическая продажа видеокурса**. Нет эквайринга, чеков, автоматической выдачи доступа, входа ученика или приватного видеохранилища. Email проверяется по формату, но владение адресом не подтверждается. Страница `course.html` остаётся публичной демонстрацией с заглушками.

## Что потребуется от владельца

1. VPS и домен; доступ выдаётся отдельно, пароли не отправлять в чат и Git.
2. Почта для технических уведомлений и рабочие контакты поддержки.
3. Выбор оплаты: банковский QR с ручной сверкой либо платёжный провайдер с API и вебхуками.
4. Для ручного режима — три QR-файла от банка (по одному на тариф), имя получателя, проверенные суммы. Из картинки невозможно программно гарантировать правильность суммы/получателя; это нужно проверить в банковском приложении перед запуском.
5. Для автоматической продажи — аккаунт провайдера и секреты, порядок чеков и возвратов, место хранения защищённых видео, правила выдачи/истечения доступа.

## Первый запуск (Linux VPS, Docker Engine и Compose v2)

Команды выполняются **из корня репозитория**. Откройте только SSH, 80 и 443. У базы и приложения в Compose нет опубликованных портов. При `TRUST_PROXY=true` приложение должно оставаться недоступным извне напрямую.

```sh
node server/setup.mjs your-domain.ru owner@example.com
```

Требуется Node.js 22.13+. Скрипт создаст `deploy/.env.production`, сгенерирует пароль БД, секрет сессий и хеш пароля администратора. Пароль администратора выводится один раз: сохраните его в менеджере паролей. Существующий файл никогда не перезаписывается. На Windows дополнительно проверьте права доступа к файлу; Unix mode там не обеспечивает ту же защиту.

Установить зависимости на сервер вручную не нужно: это делает Docker.

```sh
docker compose --env-file deploy/.env.production -f deploy/compose.yaml config --quiet
docker compose --env-file deploy/.env.production -f deploy/compose.yaml up -d --build
docker compose --env-file deploy/.env.production -f deploy/compose.yaml ps
```

До старта направьте DNS A-запись домена на IPv4 VPS. Если IPv6 не настроен, не оставляйте неверную AAAA-запись. Caddy получает сертификат для настроенного домена автоматически. Не запускайте одновременно второй веб-сервер на портах 80/443.

- Сайт: `https://ваш-домен/`
- Админка: `https://ваш-домен/admin`
- Проверка сервера и БД: `https://ваш-домен/healthz`

Миграция выполняется при старте транзакционно. Не редактировать уже применённый `001.sql`: изменения схемы оформляются отдельной следующей миграцией и обновлением загрузчика миграций.

## Подключение банковского QR без правок кода

По умолчанию `PAYMENT_MODE=disabled`: заявка отправляется, но QR для оплаты не показывается.

Положите реальные файлы в `deploy/payment-assets/`: `standard.png`, `vip.png`, `vip-plus.png`. Допустимы PNG/JPG/WebP до 2 МБ. Файлы читаются только с диска, сервер не скачивает их по произвольным URL. Не кладите туда ключи или документы.

В `deploy/.env.production`:

```dotenv
PAYMENT_MODE=manual-qr
PAYMENT_RECIPIENT='Точное имя получателя из банка'
QR_STANDARD_FILE=standard.png
QR_VIP_FILE=vip.png
QR_VIP_PLUS_FILE=vip-plus.png
```

```sh
docker compose --env-file deploy/.env.production -f deploy/compose.yaml up -d --force-recreate app
```

QR появляется **после успешной записи заявки**, соответствует выбранному тарифу. В форме показываются номер заявки, сумма и получатель. Клиентская цена и присланный статус не принимаются сервером. Тарифы заданы в `paymentPlans` в `pages/payment.js`; при изменении цен обновите также изображения тарифов, условия и банковские QR.

Администратор сверяет поступление в банке, указывает комментарий/номер операции и только затем выбирает «Оплата проверена вручную». Изменение статуса пока не отправляет письмо и не выдаёт доступ. Сохраните номер заявки для связи с плательщиком.

## Подключение провайдера позже

`POST /api/payments/webhook` намеренно отвечает 501. Непроверенное уведомление никогда не подтверждает оплату. После выбора банка/провайдера нужно реализовать отдельный адаптер: создание платежа на сервере, его связь с заявкой, проверку подписи/секрета по документации провайдера, повторную сверку суммы/валюты/получателя, защиту от повторной обработки, сверку статуса, возвраты и только затем выдачу доступа. Секреты хранятся на сервере, а не в `site-runtime.js`.

## Обновления, резервные копии и восстановление

Перед обновлением:

```sh
node server/backup.mjs
git pull --ff-only
docker compose --env-file deploy/.env.production -f deploy/compose.yaml up -d --build
```

Бэкап лежит в `deploy/backups/`; он содержит персональные данные. Настройте ежедневный запуск, ограничьте права, храните зашифрованную копию отдельно от VPS. Копирование на тот же диск не защищает от потери сервера. Скрипт не удаляет старые копии: срок хранения и удаление нужно настроить под согласованную политику.

Для восстановления используйте **новую пустую базу на отдельном сервере**, а не работающую базу клиентов. Передайте дамп в `pg_restore -U course -d course --no-owner` внутри контейнера БД. Не используйте `docker compose down -v`: это удалит том с базой. Проверьте восстановление тестово до приёма настоящих заявок.

Смена пароля: `node server/rotate-password.mjs`, заменить только `ADMIN_PASSWORD_HASH` в приватном env-файле и пересоздать контейнер `app`. Старые сессии перестанут работать. Не запускайте setup повторно ради смены пароля БД существующего тома.

## Проверки перед открытием рекламы

- Тестовая заявка видна в админке **с другого устройства**, а при недоступной БД форма не показывает ложный успех.
- Повтор той же сетевой попытки не создаёт вторую заявку; неверная почта и незаполненные подтверждения отклоняются.
- Админка недоступна без входа, выход и смена пароля отзывают доступ.
- Для каждого тарифа вручную проверены сумма, получатель и QR, затем выполнена согласованная тестовая оплата владельцем.
- Есть проверенный бэкап, мониторинг доступности, назначен человек, отвечающий на заявки.
- Утверждены документы, контакты, порядок обработки/удаления данных и ограничения курса. Техническая настройка сама по себе не подтверждает юридическое соответствие.
- До загрузки реальных видео реализованы авторизация ученика и защищённое хранение. Не помещать платные видео в `public/` или `pages/`.

## Тесты

```sh
npm ci --prefix server
node --test server/test/*.test.mjs
```

Без `TEST_DATABASE_URL` интеграционный тест PostgreSQL пропускается. Workflow `Portable server checks` поднимает отдельную тестовую PostgreSQL, проверяет миграции/конкурентные повторы/журнал/сессии и собирает Docker-образ. Он не публикует сервер и не использует реальные пароли.

`node server/test/preview.mjs` — только одноразовый локальный просмотр интерфейса на 127.0.0.1:4189 с памятью вместо БД. Не использовать как хостинг; после остановки данные исчезают.
